# Game2 v0.21.15 — независимый аудит Firebase, Worker и сообщений

**База:** точная копия полного исходного архива `Game2-Alexandra-v0.21.14-interface-redesign.zip`; изменения внесены поверх неё. Без GitHub и Cloudflare-деплоя.

## 1. Подтверждённые дефекты и исправления

### A. Сотни Firestore-операций при запуске чата

`src/storage/repositories/firestore-repository.ts`, `listPendingTurns`.

Ранее на каждый маркер незаконченного сообщения запускались два отдельных `getDoc` (user event + reply). Для `max=100` могло быть до 200 чтений документов, плюс чтение самих маркеров. Это усугубляло долгий старт, тайм-ауты и нагрузку после серии неудачных отправок.

**Исправление:** пары загружаются пакетными запросами по `documentId()` (не более 30 ID на запрос). Отбор незаконченных событий и порядок маркеров остаются прежними. Изменений данных и новых индексов не требуется.

### B. Нестабильный транспорт Firestore на мобильных браузерах

`src/storage/firebase.ts`, `getFirebaseDb`.

Ранее Firestore использовал SDK транспорт по умолчанию. Переключено на `initializeFirestore(..., { experimentalAutoDetectLongPolling: true })`, чтобы SDK мог адаптировать сетевой транспорт там, где WebChannel поток блокируется/обрывается. Это превентивное улучшение, **не доказанная единственная причина** живых ошибок `unavailable`.

### C. Несогласованные тайм-ауты и конкуренция за соединение

`src/app/store.ts`, `src/ai/cloud-language.ts`.

- Прежний лимит запуска состояния — 12 с, хотя чистым чтениям Firestore разрешено до 30 с; теперь старт ограничен 40 с, отдельное чтение редактируемого контекста — 25 с.
- Инициализация Google Auth реально ожидала всего 10 с, несмотря на объявленный 15-секундный лимит; теперь 15 с + внешняя граница 18 с.
- Клиентский лимит запроса к Worker согласован с серверным максимумом GPT и Auth: 52 с, для полного хода — 110 с.
- После *неудачного* хода фоновая maintenance теперь откладывается на 30 с, чтобы не конкурировать с ручной повторной отправкой; после успешного всё работает как прежде.

### D. Неограниченные запросы GPT в Worker

`cloudflare/worker.js`.

Текстовый запрос к OpenAI не имел AbortSignal/тайм-аута. Добавлен общий защищённый метод `openAIResponse` с ограничением 35 секунд для чата и 12 секунд для дополнительного фотопромпта. Причина отказа различается (`openai-timeout`, `openai-transport-error`, `openai-invalid-response`), вместо одного неопределённого сообщения.

### E. Легитимные длинные диалоги отбрасывались Worker

`cloudflare/worker.js`, `readPacket`.

Лимит 76 000 символов мог оказаться меньше полного контекста из истории, личности и памяти. Лимит увеличен до 160 000 символов (с предварительной проверкой Content-Length), при этом `sanitized()` по-прежнему ограничивает отдельные поля.

### F. Повторный оплачиваемый запуск фотографии по одной подписи

`cloudflare/worker.js`, `chatPhoto`.

Добавлен *best-effort* isolate-local кэш подписанных разрешений, который повторно отдаёт прежний идентификатор задачи, включая параллельные запросы в **одном экземпляре** Worker. Подтверждено тестом: два одинаковых запроса инициируют один платный запуск.

**Ограничение:** такой кэш не защищает между разными экземплярами Cloudflare Worker, перезапусками и регионами. Для строгой идемпотентности и защиты денег требуется Durable Object / серверный ledger с атомарным резервированием ключа. Не введён, поскольку потребовал бы новой Cloudflare конфигурации и мог нарушить текущий деплой.

### G. Авторизация Worker

`cloudflare/worker.js`.

Проверка Firebase Auth через Identity Toolkit при каждом запросе остаётся, поскольку удалять её небезопасно. Её сетевой тайм-аут увеличен с 4 до 8 секунд. Точечная оптимизация этого участка требует отдельного решения с локальной проверкой JWT и корректной ротацией ключей; в данном патче не делалась.

- Добавлены регрессионные тесты пакетного восстановления ожидающих сообщений, мобильного Firestore transport, ограничений GPT, легитимного контекста больше 76 КБ и повторного использования фоторазрешения.
- `node --check cloudflare/worker.js`: успешен.
- Синтаксис 64 исходных `.ts` / `.tsx`: ошибок парсинга нет.
- Полная проверка типов и production-сборка **не подтверждены**: `npm ci --offline` не смог получить отсутствующие зависимости, включая Zustand / Vite. Тесты используют установленный компилятор TypeScript только в рабочей среде; `node_modules` не включается в архив.
- Проверки с *реальным* Firebase/Auth/App Check, реальным GPT, WaveSpeed и Cloudflare не выполнялись. Никаких платных API-запросов не отправлялось.

## 4. Оставшиеся риски

1. **Критично до реальных покупок валюты:** `firestore.rules` даёт владельцу полный доступ ко всем его документам, включая тестовый кошелёк. Это допустимо для прототипа, но небезопасно для платной экономики; потребуется серверный ledger и отдельные Firestore Rules.
2. **Серверная идемпотентность платных фото остаётся неполной** между экземплярами Worker — см. пункт F.
3. **Временные сбои Identity Toolkit/App Check/JWKS не исключены.** Без логов и мониторинга развёрнутой среды нельзя доказать, что исчезли все `unavailable` и `Load failed`.
4. **Отправка GPT может быть повторена после неоднозначного сбоя сохранения:** ID сообщения защищает саму переписку, но внешняя генерация GPT не имеет глобальной дедупликации по turnId. Для строгой exactly-once семантики понадобится durable turn-state в Worker.
5. **Объём контекста GPT** остаётся связан со старыми 30 сообщениями и памятью, поэтому отдельные ответы могут быть медленными. Слепое урезание истории сознательно не выполнялось, чтобы не менять личность и память.

## 5. Как проверять на рабочем сайте

1. Одновременно обновить клиент и Worker, проверить версию `0.21.15` в настройках.
2. Открыть чат и отправить 15–20 сообщений. Следить за длительностью и повторениями; сохранять точную операцию и код из «Диагностика и подключение».
3. На телефоне переключить сеть Wi-Fi ↔ мобильный интернет, убедиться, что уже отправленное сообщение не удваивается, а неудачная попытка восстановима.
4. Запросить фото, затем при необходимости повторить именно получение уже созданного кадра; не повторять платный запуск без ID задачи.
5. Если снова возникают ошибки, нужны реальные `operation`, `code`, `elapsedMs` и версия клиента/Worker. Без этих данных нельзя приписывать всё Firebase.
